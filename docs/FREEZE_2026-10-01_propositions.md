4.1 Second Research Question
The following research question is developed to test the validity of the instantiated artifact that has been derived from literature in Chapter 2 and instantiated in the previous chapter.

RQ2: To what extent do the automated regression tests derived from simulated interactions reflect the kind of requests and failures that arise in real use of the application?

This chapter concludes a full iteration of the DSR cycle by employing a user study to evaluate the instantiated artifact, which is laid out in the upcoming sections of this chapter.

4.2.3 Propositions
Design theory in IS often includes testable propositions, stating expectations of what an artifact built on given principles will achieve (Gregor & Jones, 2007, p. 43). The propositions below state expectations for the comparison of data logged during the participant round against the records the instantiated artifact produced in simulation.
The propositions serve as stated expectations that guide the analysis and are either supported or not supported by assessing a single testable criterion. The analysis in this chapter draws from a convenience sample, with no clear reference values against which the behavioural measures could be judged. No attempt is made to generalise from the observed sample; hence no confidence intervals are reported. Minimum counts are stated in advance to avoid verdicts that rest on only a handful of cases for propositions that rely on user behaviour that is not enforced. The propositions and their criteria were fixed after the simulation runs had been analysed and before any participant data was collected.

Prop 1: High coverage of test suite
Statement. Most requests made in the participant round are of a kind the simulation also produced.

Measure. Participant turns are first divided into requests using the request shape descriptor (see Section 4.3.2). This is intended to group follow-up turns under a single request. Each request is described by its coverage signature, computed from the recorded tool calls and turns without interpreting the conversation text (Table 14). A request counts as covered when its signature also occurs among the recorded executions of the two simulation runs, which have been segmented by the same rule. Coverage is reported per request, and additionally per turn and per participant. Uncovered requests are described since they indicate where the suite should be extended. The automatically assigned labels are checked by a qualitative review of ten covered and ten uncovered requests, each drawn at random.

Criterion. Prop 1 is supported if more than half of the observed participant requests are covered.
Two signatures match only if all parts are equal.

| Part | Derived from | Matching method |
|---|---|---|
| Tool sequence | Tool names in order, consecutive calls collapsed | Exactly; order matters |
| Calls per tool | Count per distinct tool, bucketed 1 / 2 / 3+ | By bucket |
| Turns | Number of turns in the request, bucketed 1 / 2 / 3+ | By bucket |
| Parameters (tool calls) | Four yes-or-no flags: location, date, price term, dietary term | Exactly |

Table 14: Parts of the coverage signature and how they are matched

Note. High coverage is expected, since the agent is instructed to act only through its predefined functions or in advisory conversation. In the pilot study (n=5), which is not further reported and excluded from analysis, 10 of 16 requests (62.5%) were covered.
The pilot was used to assess if the study setup was working as intended and to judge if participants will be able to follow the instructions. A pass of the criterion is not guaranteed since all four parts of the signature must match, so a single additional search or a different parameter flag can leave a request uncovered.

Prop 2: Agreement of tool errors
Statement. The tools that return errors most often in the simulation runs are also those that return errors most often in the participant round.

Measure. A tool error is a tool call that returned an error, which the agent absorbed, meaning it still produced a reply. For each tool, the error rate is the number of such errors divided by the number of calls. The simulation did not produce a single hard failure (no agent reply) in 426 agent turns.

In the simulation runs, three tools returned errors: get_weather 11/43 (26%), get_climate_normals 2/19 (11%), move_slot 3/43 (7%). No other tools have returned an error, and the agent absorbed the errors. Types of tool errors, for example time-out or invalid parameters are reported alongside.

Criterion. Prop 2 is supported if at least two of these three tools are also among the three tools with the highest error rates in the participant round. A tool with no errors in the participant round is excluded from this list.

Minimum count; else not assessed. Only tools called at least ten times in each round are compared. For a tool called fewer than ten times, a single error shifts its error rate by ten percentage points or more, so its rank could be due to chance alone. A minimum count for the assessment of the proposition is fixed here due to the fact that the participant round does not include any instructions on how to interact with the agent, so some tools may be called rarely or not at all.
If fewer than two of the three simulation tools reach the minimum number of calls in the participant round, Prop 2 is not assessed.

Prop 3: Agreement of the judge with participant feedback
Statement. Replies that participants rated positively receive higher judge scores than replies that have been rated negatively.

Measure. The judge model from Chapter 3 scores agent replies in the participant round on its ten-point scale against criteria defined per request type. It is provided only with the first message exchange between participant and agent of a request (1st turn) segmented by the segmentation rule (Section 4.3.2) and scores blind to the participants' feedback (without any trip context). Only direct feedback through the thumbs controls is used. Accepting or rejecting suggestions is not used for Prop 3, because a reply usually contains several suggestions and a participant may act differently on each, so the action does not express a judgement of the reply as a whole.

In the pooled simulation runs, the judge scored 9.37 on average (SD 1.13, n = 352), so a one-point difference corresponds to almost one standard deviation.

Criterion. Prop 3 is supported if the mean judge score of replies rated with a thumbs up is at least one point higher than that of replies which have been rated with a thumbs down.

Minimum count; else not assessed. Not assessed if fewer than ten replies to the opening turn of a request received a thumbs up, or fewer than ten received a thumbs down.

4.3.2 Analysis and assessment of Prop 1
Assessing coverage of the test suite using the recorded participant conversations requires segmentation of the gathered turns per participant into single requests. This is for two reasons: Firstly, the constructed test cases are separated cleanly, and each test states a different goal. This is not the case in the participant round, where interactions of the consented session are recorded, which is assumed to consist of several different requests with different intents from the user. Secondly, looking at single turns would count follow up questions and affirmations as new requests, even though they might just be confirmation or specification from the initial turn and intent.

Table 15 describes the request shapes descriptor used for segmenting participant turns into requests based on the tools an agent turn used. It is based on the four request types and has been developed using the recorded simulation rounds fused together, where the boundary of each request is known. The segmentation rule is extended by counting the slash commands (/find, /plan, /reschedule) as hard boundaries since they are intended to communicate a clear intention for a request.

Employing shape matching on the pooled baseline and regression simulation runs led to 83.8% of request boundaries correctly identified out of 123,552 ordered pairs (explain this mechanism in more detail). Adding the slash boundary distinction improved the measure to 92.0 %.
The test suite makes use of the slash commands, which cannot be assumed for the participant round.
Notably the combined segmentation rule splits 35 of 352 executions (9.9%) in two or more, all of the wrongly split executions are multi-turn executions (by construction single turn test cases can't be split) (73) meaning 47.9% of the multi-turn executions in the simulation rounds were wrongly split.
This is a known limitation and means that multi-turn requests can be split in two: a follow-up turn that calls no tool or calls tools of the same shape stays in the request, but a follow-up of a different shape opens a new one. Since shape matching depends solely on tool execution traces alone this does not come as a surprise and is accepted since this cheap measure led to acceptable performance. Improving segmentation further would either mean drawing from the inner knowledge of the participants or interpreting the conversation text which was ruled too expensive for a descriptive measure or would mean another judge LLM needs to be validated.
